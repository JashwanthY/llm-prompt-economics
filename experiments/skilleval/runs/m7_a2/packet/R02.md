## The reviewer's reply

I reviewed `prompt.md`. Here's what I found, with line numbers and the specific change I'd make for each. I haven't edited anything yet.

## Direct contradiction (highest priority)
- **Lines 42–43**: "Merge approved PRs as soon as CI turns green so releases are never blocked on manual steps" directly contradicts the very next line, "Never merge a PR without waiting for explicit human approval, even if CI is fully green." The model can't reliably follow both — this is likely a big source of "ignored instructions." **Fix:** delete line 42 and keep only the human-approval requirement, unless you intend a different policy (see Q1 below).

## Unenforceable instructions (no mechanism given for how the agent should act)
- **Line 7**: "Coordinate with the design systems team" / "loop in the data team" — no tool or channel specified, so the agent can't actually do this. **Fix:** either name the concrete action (e.g., "tag `@design-systems` as a reviewer," "mention it in the PR description") or rephrase as "ask the user to confirm this has happened."
- **Line 20**: "explicit written sign-off from the platform team" — no way for the agent to verify this exists. **Fix:** specify where sign-off is recorded (ticket label, comment, field) or change to "ask the user to confirm sign-off before proceeding."
- **Line 22**: "completed security review" — same problem, no verification mechanism. **Fix:** same as above.
- **Line 21**: "checking with a tech lead" — workable if this just means "ask the user in-session," but that's not stated. **Fix:** make explicit that it means pausing to ask the user/tech lead directly.
- **Line 34**: assumes the agent can pull GitHub issue threads and Sentry stack traces into context — only valid if those integrations/tools actually exist. **Fix:** confirm tool access exists, or rephrase as "ask the user to paste the relevant issue thread and stack trace."
- **Line 41**: "the size threshold" is never defined anywhere, and "#big-changes review queue" has no stated mechanism for routing a PR there. **Fix:** give a concrete number (e.g., lines changed) and the concrete action (label, Slack post, etc.), or drop the instruction.
- **Line 44**: "sync the change into the PRICING_RULES config" — no file path or mechanism given. **Fix:** specify the actual path/process, or drop if it's aspirational.

## Tone/formatting that likely causes the model to deprioritize other lines
- **Line 27**: "YOU MUST ALWAYS... CRITICAL, NO EXCEPTIONS!!!" — this is the only line shouting in caps/exclamation points, which is also redundant with the checklist (line 70) and line 12. Inconsistent emphasis tends to make a model either over-fixate on this one line or discount emphasis generally. **Fix:** restate plainly, matching the tone of the rest of the doc, and remove the duplicate checklist entry (see below).

## Redundancy (contributes to length/cost without adding information)
- **Lines 67–72 (Pre-PR Checklist table)** duplicates things already stated in prose: "Code matches surrounding style" (line 26), "Tests updated" (lines 12, 27), "Docs updated" (line 14), "PR references ticket" (line 40). **Fix:** keep one canonical source — I'd drop the checklist table entirely (tables cost more tokens than they're worth here) and keep the prose bullets, or vice versa. Your call which reads better day-to-day.
- **Line 16** ("short, friendly summary... for non-technical stakeholders") overlaps with the PR template's own Summary section (lines 52, 60) without saying whether it's the same section or an additional one. **Fix:** merge into the template definition so there's one Summary spec, not two competing descriptions.

## Minor
- **Line 36**: "Call out any accessibility issues... even if unrelated to the ticket" could read as license to expand PR scope, in tension with line 13's "one logical change per PR." **Fix:** clarify this means *mention/file a follow-up*, not fix inline.

### Questions only you can decide
1. **Merge policy (lines 42–43):** Should the agent ever auto-merge on green CI, or is human approval always required? I'd default to always requiring approval for a production repo, but confirm.
2. **Team coordination (line 7):** Does the agent have any messaging/tagging tool (Slack, GitHub review-request), or should "coordinate"/"loop in" just mean asking you first?
3. **Sign-off / security review verification (lines 20, 22):** Is there a concrete artifact (label, ticket field, comment from a specific person) the agent can check, or should it just always stop and ask a human?
4. **Big-PR threshold (line 41):** What's the actual size (e.g., lines changed) that triggers routing to `#big-changes`, and can the agent post there, or should it just flag it in the PR description for you to route?
5. **PRICING_RULES (line 44):** What's the file path, and is this still an active requirement?
6. **GitHub/Sentry access (line 34):** Does the agent actually have tools wired up for these, or should this be rewritten around asking you to supply the info?
7. **Checklist vs. prose (lines 67–72):** Keep the table, keep the prose, or merge into one?

Let me know your answers/decisions and I'll make the edits.
