## The reviewer's reply

I reviewed `prompt.md` (73 lines). Here's what I found, with line numbers, before touching anything.

## Contradictions (highest priority — likely why the model "ignores parts")

- **Lines 42–43**: directly contradictory. Line 42 says merge as soon as CI is green "so releases are never blocked on manual steps"; line 43 says never merge without explicit human approval "even if CI is fully green." A model given both will pick one unpredictably. **I need you to tell me which policy is actually correct** — my guess is 43 is correct and 42 should be deleted, but I don't want to assume.

- **Line 16 vs. Line 52**: Core Responsibilities says to add "a short, friendly summary at the top of each PR for non-technical stakeholders," but the PR Template's **Summary** section (line 52) is described as "one paragraph describing the change and why it's needed" — not specified as stakeholder-friendly. This reads as two different summaries. **Is there really supposed to be two summaries, or should line 16 just be folded into the template's Summary section?**

## Instructions the agent likely can't actually execute

These describe actions the agent has no tool/mechanism to perform, which is a common cause of a model "ignoring" instructions — not defiance, just no path to comply:

- **Line 7**: "Coordinate with the design systems team" / "loop in the data team before changing anything under `apps/web/analytics`" — coordinate *how*? Is there a Slack/ticket integration, or should this just become "ask the user to confirm before proceeding"?
- **Line 20**: "without explicit written sign-off from the platform team" — how would the agent obtain or verify this?
- **Line 21**: "without first checking with a tech lead" — same issue.
- **Line 22**: "without a completed security review" — how does the agent confirm a review is "completed"?
- **Line 34**: "pull the full GitHub issue thread and any linked Sentry stack traces into your working context" — does this agent actually have GitHub/Sentry access configured? If not, this is dead weight.
- **Line 44**: "sync the change into the PRICING_RULES config" — does this config exist and is it reachable by the agent, or is this aspirational?

**My question for all six above:** does the agent have real integrations for these (Slack, GitHub, Sentry, a config repo), or should they all be rewritten as "ask the user/a human for explicit confirmation before proceeding"? That's a one-line fix applied consistently, but I want your call before rewriting restriction/approval language.

## Undefined terms

- **Line 41**: "exceeds the size threshold" — no threshold is defined anywhere. Either give me a number (e.g., lines changed, files touched) or I'll recommend removing the clause as unenforceable.

## Style/tone bloat (token cost + likely causes the model to skim)

- **Line 27**: `YOU MUST ALWAYS run the full test suite before opening a PR — CRITICAL, NO EXCEPTIONS!!!` — shouting/caps/exclamation stacking is exactly the kind of boilerplate-sounding text models learn to skim past. I'd rewrite as a plain, flat imperative sentence, same weight as everything else.

- **Line 69** ("Code matches surrounding style") duplicates line 26; **line 70** duplicates line 12/14; **line 72** duplicates line 40. The checklist is meant as a condensed recap, so some overlap is fine, but if we're cutting cost I can tighten the checklist to reference the sections above instead of restating them.
